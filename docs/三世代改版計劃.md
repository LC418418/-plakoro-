# 三世代改版計劃（關都 + 城都 + 豐緣）

由「一個關都八館」擴成「三個世代各八館 + 魔鬼模式打通 24 館」嘅可行性研究
同分階段交接文件。

**點用呢份文件**：每個階段開一個**新嘅 Claude session**（唔好接住舊嘅），
第一句就打「睇 `docs/三世代改版計劃.md`，做階段 X」。
（八館改版嗰次證實咗：新 session 平均每次呼叫嘅 context 少一半以上，
同樣工作量平大約一半。呢次個檔更大，慳得更多，見第六節。）

---

## 一、一句話結論

**做得到，冇技術死位**，但唔係一個 session 做得完嘅嘢。

最重要嘅發現有三個：

1. **招式唔使人手寫。** `subType()` / `genPlayable()`（`index.html:1602-1797`）
   係「種子式生成器」—— 加一行圖鑑資料，佢自動出一套招式同骰組，
   同一隻永遠出同一套。加 235 隻新寶可夢嘅**招式成本接近零**。
2. **屬性唔使加。** 遊戲用緊 10 個自訂屬性（草炎水雷超闘悪鋼空無），
   官方 18 個屬性早就映射咗落去（冰→水、龍→空、蟲→草、毒→悪、
   地面→闘、岩石→無、幽靈→悪）。第二、三代冇引入新屬性，
   `TYPES` 一個字都唔使改。
3. **真正嘅成本喺三度**：圖（+437KB base64）、平衡（三個世代 × 八館要逐個量）、
   同排行榜嗰堆歷史包袱（`bestSnapshot` 三重防守嗰段，撞過兩次）。

**預計**：7 個階段、大約 **11-14 個 Claude session**，
你自己落手嘅時間主要係「校中文名」同「Firebase Console 貼規則」。

## 三、可行性逐項評估

### 3.1 加寶可夢資料（第二代 100 隻、第三代 135 隻）　**易**

現況（`index.html:1411`）：

```js
const DEX_RAW = [
[1,'妙蛙種子','草',1],[2,'妙蛙草','草',2],[3,'妙蛙花','草',3],
```

四個欄位：編號、名、屬性、進化階段（1/2/3，4 = 神獸），第五個可選係弱點覆寫。
加 235 行就搞掂，加上 `EVO`（`index.html:1511`）嘅進化鏈。

**唔好人手打字。** 寫一個 `tools/gendex.py`，由 PokeAPI 嘅
`pokemon-species` 攞官方繁中名（`names[zh-Hant]`）、屬性、進化鏈，
用下面張映射表出 code。人手打 235 行 = 燒好多 token 兼一定有錯。

**屬性映射表（18 → 10）**，由現有關都資料反推出嚟，唔係我砌嘅：

| 官方 | 遊戲 | 憑咩 |
|---|---|---|
| 一般 | 無 | 拉達 19/20 |
| 火／水／草／電／超能力 | 炎／水／草／雷／超 | 直接對應 |
| 格鬥 | 闘 | 希巴「四天王・鬥」`type:'闘'` |
| 飛行 | 空 | 波波 16-18 |
| 毒 | 悪 | 阿柏蛇 23 |
| 地面 | 闘 | 坂木「地面道館」`type:'闘'` |

即係 `TYPE_FOCUS`（`index.html:3535`）嗰行**一定要重新校**，
而且鋼系終於夠開一個道館（城都第 6 館阿蜜）。

### 3.2 圖（pixel art）　**中等，但係整個計劃嘅樽頸**

**現況實測**：`DEXSPR`（`index.html:1290`）係**一行** JSON，151 隻
40×40 PNG base64，共 **281KB**，平均每隻 1,861 個 base64 字元。
成個 `index.html` 而家 **1.83MB**，入面 **1.22MB 係圖**：

| 位置 | 內容 | 大細 |
|---|---|---|
| `index.html:1795` | `SCENES` 戰鬥背景 | **745KB** |
| `index.html:1290` | `DEXSPR` 151 隻精靈 | **281KB** |
| `index.html:191` | 主畫面背景 | **178KB** |
| `index.html:1289` | `FACE_IMG` 骰面 | 13KB |

加 235 隻 → **+437KB** → `index.html` 變 **2.27MB**。

⚠ **`sw.js` 係 network-first**（有網就攞最新）。即係玩家**每次開機**
都會重新下載成個 `index.html`。而家已經係 1.83MB，加到 2.27MB
喺 iOS 手機數據上會好明顯。**呢個係要喺階段 0 處理嘅前置條件**，
唔係「順手做」。

**圖源調查**（你叫我搵嗰樣）：

| 來源 | 尺寸 | 齊唔齊 | 評價 |
|---|---|---|---|
| [PokeAPI/sprites](https://github.com/PokeAPI/sprites) `versions/generation-iii/firered-leafgreen` | 64×64 | **1-386 全齊** | ⭐ **建議用呢個。** 火紅葉綠正正就係你講嘅第一代版本，而佢有齊到第 386 號，三個世代**美術風格完全統一** |
| PokeAPI `versions/generation-ii/crystal` | **40×40** | 只有 1-251 | 尺寸同現有嘅一模一樣（現有 151 張好可能就係由呢度嚟），但冇第三代 |
| [smogon/sprites](https://github.com/smogon/sprites)（Pokémon Showdown） | gen3 64×64／gen5 96×96 | 齊，仲有動畫 | gen5 質素最高但風格同現有嘅唔夾；動畫版體積大好多 |
| [msikma/pokesprite](https://github.com/msikma/pokesprite) | 68×56 box sprite | 齊 | Q 版盒仔圖，同現有戰鬥圖風格唔同 |

只喺同事之間玩、冇收錢 —— 加多兩代**唔改變性質**。照做，但唔好放上
app store 或者賣廣告。

### 3.3 三個世代獨立挑戰　**中等偏難（最重嗰個階段）**

要抽一個 `REGION` 層出嚟：

```js
const REGIONS = [
  { id:0, n:'關都', gyms:GYMS_KANTO, e4:E4_KANTO, champ:CH_KANTO,
    starters:[1,4,7],     dex:[1,151],   focus:FOCUS_KANTO },
  { id:1, n:'城都', gyms:GYMS_JOHTO, ... starters:[152,155,158], dex:[152,251] },
  { id:2, n:'豐緣', gyms:GYMS_HOENN, ... starters:[252,255,258], dex:[252,386] },
];
```

改動範圍（grep 數過）：`ACTS` 出現 **48 次**、`GYMS` **6 次**、`DEX[` **19 次**。
`GYMS` 少係好消息 —— 但 `ACTS` 48 次要留返階段 5 先郁（見下）。

**要跟住改嘅位**：

- `run.gen` 落存檔 → `SAVE_VER` 由 4 升到 **5**
  （⚠ `SAVE_MIN_VER` 唔好一齊升，唔係人哋玩緊嗰局會俾剷走）
- 名人堂由 3 格變成**每世代 3 格**：`plakoro.hof.<gen>.<i>`、
  雲端 `users/<uid>/teams/<gen>/<i>` —— **要寫 migration**
  （舊 `teams/0-2` 當成 `teams/0/0-2`，即係關都）
- `tools/simlib.js` 加 `gen` 參數（佢已經冇寫死道館，只係用 `ACTS`／`ELITE4`，
  改動細）

**難度「同第一世代相約」**：`TIER` 四個端點 + `ACT_TUNE` 兩行照用同一套，
唔使每代一套。**要重新校嘅只有 `TYPE_FOCUS`**（池大細變咗）同每代嘅
凸位／凹位（好似關都第 4 章莉佳因為草系易剋而凸咗嗰種）。

⚠ **三個世代都會撞「兩館同屬性」**（同關都撞過嗰個一樣）：

| 世代 | 撞邊兩館 |
|---|---|
| 城都 | 第 1 館阿速（飛行→空）vs 第 8 館小椿（龍→空） |
| 豐緣 | 第 1 館千里（岩石→無）vs 第 5 館千歲（一般→無） |

同關都「小剛 vs 坂木」一樣，跟返上次嘅決定 B（就咁擺住，靠 `TYPE_FOCUS`
分開強度）就得。

⚠ **城都四天王同關都撞名**：阿桔（Koga，關都第 5 館館主 → 城都四天王）、
希巴／志清（Bruno，兩代都係四天王）、渡／阿渡（Lance，關都四天王 →
城都冠軍）。原著本來就係咁 —— 呢個係**特色唔係 bug**，
但你要決定顯示嗰陣點寫（見第四節決定 3）。

### 3.4 魔鬼模式改成 24 館通天塔　**難（風險最高）**

呢個係最大嘅改動，因為 `ACTS` 由「編譯時常數」變成「一局嘅屬性」。
48 處引用要逐個睇，而且好多喺排行榜嗰邊（`ACTS+1` = 通關）。

**設計上嘅新嘢**：

- 隊伍唔再係「三選一抽卡」，係由三個世代嘅名人堂**各揀 2 隻**（硬性）
- 一局 24 章 × 6 關 ≈ **96 場以上**（而家八館制係 32 場）—— 一局玩幾個鐘
- 25 個 boss（24 館主 + 最終）要一條新曲線
- 通關率預計會低到量唔到（後半樣本本身就薄）

⚠ **同現有嘅設計原則有衝突**，要你拍板（見第四節決定 1）：
`index.html:4442` 個註解明文寫住「名人堂讀返出嚟淨係打得對戰，
接唔返落挑戰模式。呢個限制係故意嘅：一但接得返，就等於 save/load 番晒嚟，
永久死亡就冇曬意思」。魔鬼模式用名人堂隊伍就係破咗呢條規。

### 3.5 排行榜改版　**中等，但係最易靜靜雞出事嗰個**

現況（`index.html:6072-6160`）已經有三重防守，係撞過兩次真事之後補返嘅：
`FB.rogue === null` 唔寫榜、`plakoro.best.<uid>` 本機鏡像取大、
`wins > 0` 就一定顯示通關。呢三層**全部都要跟住改**。

**新排序**（你要嘅）：魔鬼完成 → 完成幾多個世代最終 boss → 徽章數 → …

**新欄位**：

| 欄位 | 型 | 做咩 |
|---|---|---|
| `gauntlet` | number 0/1 | 魔鬼通關咗未 |
| `gens` | number 0-7 | 三個 bit，邊幾個世代打爆咗最終 boss |
| `badgeMask` | number 0-16777215 | **24 個 bit**，邊幾個道館拎過徽章 |

⚠ **「重新挑戰獲得嘅徽章唔重複計算」呢個要求，逼住要用 bitmask。**
而家個 `badges` 係一個數字（`Math.max(...)`），重打第 3 館攞多次
一樣會計。改成 24-bit mask 之後 `popcount(mask)` 就係真正嘅徽章數，
天然唔會重複。

⚠⚠ **`database.rules.json` 個 `board` 節點有 `$other: false`。**
新欄位唔喺 rules 度列明，**成個寫入會俾人拒絕，而且唔會報錯，
個名就係唔更新**。而且 `badges` 上限而家寫住 `<= 8`，要改到 `<= 24`。
改完 **要你自己去 Firebase Console 貼**，唔會自動生效。

### 3.6 新技能　**易，但會推翻平衡**

`MV_T`（`index.html:3264`）10 個模板、`PMV`（`index.html:1642`）玩家招式池、
`TYPE_FLAVOR` 負責換名。加新模板本身好易，但**每加一個都要重跑
`measure.mjs` 對返八個數**。所以擺喺平衡校完之後做，唔好撈埋一齊。

## 四、⚠ 五件事要你先決定

呢五樣唔決定就做唔落。

### 決定 1：魔鬼模式用名人堂隊伍，等於破咗「唔准 load」嘅規矩

現有設計係「永久死亡」：名人堂只可以打對戰，接唔返落挑戰。
你要嘅魔鬼模式係直接用名人堂六隻去打 24 館。

- **A（建議）**：魔鬼模式係**獨立終局挑戰**，入面**唔可以捉新寶可夢、
  唔會進化／特訓**（六隻本身已經係練成品），但照有遺物／商店／道具袋。
  即係「用你練成嘅隊伍去考試」，唔係「load 咗個檔繼續練」。
  永久死亡嘅精神喺三個世代嗰邊照樣守住。
- **B**：照舊會成長。咁魔鬼模式就變咗最抵玩嘅練功模式，
  三個世代反而冇人打。
- **C**：魔鬼模式輸咗就要重新用**新一次**通關嘅隊伍先入到（消耗名人堂）。
  最狠，但同事之間可能玩到嬲。

### 決定 2：加咗二三代之後，關都嗰局會唔會撞到二三代寶可夢？

- **A（建議）**：唔會。關都局只抽 1-151，城都局只抽 152-251，
  豐緣局只抽 252-386。乾淨、好平衡、亦都最貼「獨立挑戰」個講法。
- **B**：城都局可以撞到關都嘅（原著金銀就係咁）。池大好多，
  但平衡要重新量，而且「玩多啲新寶可夢」呢個目的會被溝淡。

### 決定 3：撞名點顯示

阿桔（關都第 5 館 → 城都四天王）、希巴／志清（Bruno）、渡（關都四天王 →
城都冠軍）。

- **A（建議）**：照原著，重複就重複。玩開嘅人會覺得「係喎，佢升咗職」。
- **B**：城都嗰邊改個名避開。

### 決定 4：要唔要順手換走現有 151 張圖，統一做火紅葉綠風格

火紅葉綠（`generation-iii/firered-leafgreen`）有齊 1-386，
三個世代美術**完全一致**。但現有 151 張玩開嘅圖會變樣。

- **A（建議）**：全部換成火紅葉綠。你自己都講第一代係「火紅葉綠版關都」，
  正好對應。而且淨係要跑一次腳本。
- **B**：關都保留現狀，城都用金銀水晶（40×40 原生），
  豐緣用火紅葉綠縮圖。省事但三代風格唔統一。

### 決定 5：`index.html` 唔再係單一檔案（階段 0）

要拆走嗰 1.22MB 圖做外部檔。好處係玩家每次開機唔使再下載成 1.2MB
（圖用 cache-first + 版本化檔名），壞處係 `CLAUDE.md` 講嘅
「單檔網頁遊戲」呢個特性冇咗。

**強烈建議做**：唔做嘅話，加完二三代之後每次開機要落 2.27MB，
而且之後每個階段 Claude 讀個檔都會貴一大截（見第六節）。

## 五、七個階段

> 每個階段一個新 session。每個階段做完**都應該可以出版**（`sw.js` 加版本號），
> 唔會出現「做到一半玩家玩唔到」。

### 階段 0：拆走圖，起返個地基　　**1 session**

**做咩**：`SCENES`／`DEXSPR`／主背景／`FACE_IMG` 由 `index.html` 搬去
`assets/scenes-v1.js`、`assets/dexspr-v1.js` 等等。`sw.js` 對呢批
用 **cache-first**（因為檔名帶版本號，改咗就係新檔），`index.html` 維持
network-first。

**點解擺第一**：

- `index.html` 由 1.83MB 跌到大約 **600KB** → 玩家每次開機平 1.2MB
- 之後每個階段 Claude grep／read 個檔都平好多 → **直接慳你 usage**
- 純搬運，冇邏輯改動，風險最低，最啱做第一步

**驗收**：三個 test 全綠、GitHub Pages 上載完離線照玩、iOS 加到主畫面照玩。

**風險**：低。唯一要小心係 GitHub Pages 嘅相對路徑同 PWA scope。

### 階段 1：圖 + 資料管線　　**1-2 sessions**

**做咩**：

1. `tools/fetchdex.py` —— 由 PokeAPI sprites 攞 1-386 火紅葉綠圖，
   縮到 40×40、減色、出 `assets/dexspr-genN-v1.js`
2. `tools/gendex.py` —— 由 PokeAPI species 資料出 `DEX_RAW` 同 `EVO` 嘅
   第二、三代部分（繁中名自動攞，屬性用第三節張表映射）
3. 中文名**你人手掃一次**（官方譯名有時同大家叫開嘅唔同）
4. 圖鑑畫面（`openDex`）睇到三代全部 386 隻

## 六、點樣慳 usage（你問嘅重點）

### 6.1 最大嗰筆：階段 0 拆走圖

`index.html` 而家 1.83MB，入面 1.22MB 係 base64。
每次 Claude 要 grep／睇個檔嘅結構，都要喺呢舊嘢中間游水。
`CLAUDE.md` 本身都要用一整節去教「唔好 cat、唔好 grep 到 base64 嗰幾行」。

拆走之後個檔剩 ~600KB。**之後六個階段每一個都平** —— 呢個係
一次投資、六次回報。

### 6.2 每個階段開新 session

八館改版嗰次量過：新 session 平均每次呼叫嘅 context 少一半以上，
同樣工作量平大約一半。呢份文件就係為咗令新 session 唔使重新摸底。

### 6.3 資料錄入要用腳本，唔好人手打

235 行 `DEX_RAW` + 進化鏈人手打，係幾萬個 token 嘅輸出，而且一定有錯，
錯咗要改又要再燒一次。寫個 60 行嘅 Python 由 PokeAPI 生成，**平幾十倍**。
同一個道理套喺 235 張圖度。

### 6.4 平衡放最後，而且用模擬器

模擬器跑幾多局**完全唔影響 usage**（返嚟都係同一舊細 JSON）。
所以：

- 結構（階段 2）同平衡（階段 3）**分開做**，唔好一路寫一路調
- 一次 sweep 塞多幾組設定去試，唔好一次試兩三組
- 局數 3000 起跳，唔好慳

### 6.5 每個階段獨立可出版

咁樣就算你中途想停低唔做落去，之前做嘅嘢一樣落到玩家手。
唔會出現「投資咗一半，冇嘢見到」。

### 6.6 唔好一個 session 做兩個階段

尤其係階段 2（世代化）同階段 5（24 館）—— 兩個都係大範圍改動，
撈埋一齊 context 會爆，出錯之後要重讀成個檔，反而更貴。

## 八、風險同陷阱（做之前一定要知）

1. **`board` 加欄位一定要重貼規則。** `$other: false` 會靜靜雞拒絕成個寫入，
   唔報錯，個名就係唔更新。撞過。
2. **排行榜三重防守唔可以拆。** `FB.rogue === null` 唔寫榜、本機鏡像取大、
   `wins > 0` 一定顯示通關 —— 呢三層係真事撞出嚟嘅
   （有人打爆冠軍之後個榜寫返「第 8 道館」）。加世代欄位嗰陣要三層一齊改。
3. **`SAVE_MIN_VER` 唔好隨手升。** 升咗＝人哋玩緊嗰局俾剷走。
4. **`tools/simlib.js` 要跟住遊戲改。** 佢自己重寫咗寶箱／商店／換人嗰幾段。
   遊戲加咗新嘢佢冇跟，量出嚟嘅通關率會偏低而且**唔會報錯**。
5. **平衡對數值極敏感**：魔鬼第 1 章 `dmg` 加 0.01 通關率跌 15 點。
   血量一行 0.02-0.05、傷害 0.01-0.02，兩樣分開試。
6. **後面幾章樣本天生細**：6000 局先得 ~120 局行到第 8 館。跳 ±10 點係雜訊。
   24 館通天塔呢個問題會更加嚴重 —— 可能要 50000 局先有得睇。
7. **加新資源要三個位一齊改**：`ITEMS`／`CHEST_LOOT`／`openShop`，
   加埋 `serializeRun` + `deserializeRun`，同埋 `tools/simlib.js`。
8. **GitHub Pages 派 `main`。** 喺 branch 做完記得 merge 返落 `main`
   （撞過：做完冇 merge，玩家一直行緊舊 code）。
